The 802.11 Model
================

Sending and Receiving 802.11 Frames
-----------------------------------

The MAC exchanges :cpp:`Packet` objects containing typed IEEE 802.11 header and
trailer chunks.  Local transmission requests and reception indications are
carried by tags; the selected PHY mode and HE user allocation remain PHY
authorities and are not reconstructed from MAC configuration.  A frame
sequence describes the ordered transmit and receive steps, while the HCF
exchange engine owns the active sequence, response timers, completion, and
abort processing.

Architecture of the 802.11 MAC Model
------------------------------------

The NED-facing ``Hcf``, ``VhtHcf``, and ``HeHcf`` module types preserve the
configuration interface used by existing networks.  Their ``featureSet``
submodule implements :cpp:`IHcfFeatureSet` and advertises genuine prepared
exchange providers through :cpp:`IHcfExchangeProvider`.  Provider descriptors
are sorted by the fixed semantic exchange-class order, independently of NED
declaration or construction order.  Direct ordinary SU, channel release, HT
sounding, and VHT sounding are not provider descriptors.  Duplicate classes,
non-transactional descriptors, and non-executable descriptors are rejected
during initialization.

Exchange selection separates probing from execution.  A provider receives an
immutable :cpp:`HcfContext`, validates eligibility without changing queues or
consuming random numbers, and either reports a typed rejection or returns a
prepared transaction.  The transaction is committed only after capability,
PHY, duration, and ownership validation.  Typed VHT and HE callbacks report
member transmission, per-user response, timeout, completion, and rollback;
frame sequences do not discover collaborators by walking the module tree.

Baseline SU and HT/VHT sounding use direct explicit frame sequences.  VHT and
HE operations that reserve or coordinate multiple owners use prepared HCF
transactions.  VHT sounding protects its dialog token with a local rollback
guard; it is not an HCF transaction.  HE per-STA SU fallback remains
transactional when it carries a prepared provider start.

The direct path is ``channel grant -> validation -> explicit frame sequence ->
exchange engine``.  A prepared path adds immutable snapshot selection and
transaction validation before the exchange engine takes ownership.  Only a
selected genuine provider crosses the transaction commit boundary, and the
engine subsequently delivers exactly one terminal result to the selector for
transactional exchanges.

IHcfFeatureSet providers no longer replace ordinary SU, channel release, HT
sounding, or VHT sounding.  They remain extension points for genuine prepared
VHT/HE exchanges.  No compatibility mode is provided.

HCF specializations and MAC schedulers
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The HCF amendment types are a composition boundary, not one large inheritance
tree.  ``VhtHcf`` and ``HeHcf`` preserve the NED-facing drop-in types, while
the common ``Hcf`` creates the amendment runtime and feature-set components
selected by configuration.  HT behavior is concentrated in the HCF-owned
:cpp:`HtHcfFeature`; VHT uses the private ``HcfVhtRuntime`` adapter and
:cpp:`VhtHcfFeature`; HE uses :cpp:`HeHcfRuntime` and its services.

The scheduler path starts only after EDCA has selected an access category and
won a TXOP.  EDCA/EDCAF and :cpp:`Contention` own channel access, backoff,
retry, and TXOP state.  VHT and HE schedulers consume immutable candidate and
PHY snapshots inside that TXOP.  VHT selects a compatible group of DL MU-MIMO
users.  HE downlink schedulers return per-STA RU, MCS, spatial-stream, and
duration allocations; HE uplink schedulers return scheduled or random-access
RUs plus common HE-TB timing.  The amendment exchange service validates and
commits those results before packets, sequence state, or scheduler-observation
state are advanced.

The current HE NED defaults select :cpp:`HeDlSchedulerEqualSizedRUs` for
downlink and :cpp:`HeUlSchedulerBacklogBased` for uplink; the scheduler modules
remain replaceable through the HE coordinator configuration.

HE uplink random-access allocations carry an explicit target policy.  The
default ``associated`` target continues to use AID12=0.  An ``unassociated``
target uses AID12=2045 and is restricted to one pending management S-MPDU
addressed to the triggering AP; its terminal Multi-STA Block Ack uses the
preassociation record form with the station address.  Association identity,
Trigger transmitter, received HE BSS color, and queue ownership are kept as
separate transaction inputs so that a foreign AP cannot reuse an associated
station's epoch or data queue.

State and packet ownership
~~~~~~~~~~~~~~~~~~~~~~~~~~

Each mutable state has one owner:

* EDCA and its EDCAFs own contention, the winning access category, retry
  counters, and TXOP state.
* The HCF exchange engine owns the active frame sequence and response timers.
* Originator and recipient Block Ack handlers own their respective agreements
  and windows.
* HCF owns ingress tracking, originator/recipient dispatch, aggregation, and
  transmission preparation; these remain factored into services and are
  invoked through HCF-owned action adapters.
* HE peer, queue, sounding, downlink-MU, and triggered-uplink services own their
  amendment-specific lifecycle and transaction state.
* The PHY mode objects own legal mode combinations, duration calculations, and
  PPDU timing; HCF stores the selected mode reference needed by the active
  direct or transactional sequence.

A packet reservation records packet identity, source queue, association epoch,
and transaction generation when a prepared exchange needs them.  Direct
transmission preparation uses one borrowed handoff and keeps the source packet
identity in the existing queue and retry owners.  Prepared exchanges commit
every reserved packet exactly once; their failures roll back queue order,
packet identity, sequence numbers, retry state, and Block Ack state.  Late
callbacks are rejected using the transaction identity.  Semantic signals are
emitted once by the component that owns the corresponding action.

When a selected feature has staged state, its provider or amendment runtime
rolls that state back before packets are returned to their recorded source
queues in original order and cloned sequence or retry state is discarded.
Rollback never emits successful-transmission observations and never re-runs
provider selection.

Adding an amendment exchange
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Add a new exchange without extending the HCF facade with amendment-specific
fields or virtual methods:

#. Define immutable snapshot, plan, rejection, and result types for the
   amendment decision.
#. Implement a provider behind :cpp:`IHcfExchangeProvider`; keep scheduling
   separate from PHY finalization and packet commit.
#. Add typed callback and action contracts for effects owned by common MAC
   services.  Inject rate selection and other collaborators explicitly.
#. Register the provider in an interface-typed feature-set implementation and
   add its semantic class to the fixed selection order.
#. Preserve the common single-user fallback and gate the provider on operation
   mode, local role, and negotiated peer capabilities.
#. Add focused tests for eligibility, failure and rollback, stale callbacks,
   AP and non-AP roles, feature-off behavior, legacy fallback, and deterministic
   tie-breaking.  Keep a compatibility test for any retained public NED
   typename.
