## P8 implementation contract

`LowpanContextTable` stores at most 16 canonical IPv6 prefixes of lengths 0–128, absolute validity deadlines and a compression permission. `LowpanLayer` owns one table per interface and loads an optional XML `compressionContexts` parameter at initialization. Codec lookups take explicit simulation time; missing/expired contexts reject context-dependent decoding, while context-independent unspecified source and unused CID values preserve current behavior. The context identifier octet follows RFC 6282 section 3.1.2. Multicast context prefixes are limited to the 64-bit prefix field of the RFC 3306/3956 representation.

The owner exposes a typed context-install operation for future ND updates. Prefix/length replacement clears partial receive state and cancels its timer; validity/permission refresh does not reinterpret stored bytes. A FRAG1 decoded while its context is valid already contains the reconstructed IPv6 address, so later expiry cannot change that snapshot. FRAGN-first storage is invalidated by prefix replacement before a later first fragment can mix generations. Static configuration persists through ordinary lifecycle cleanup, with absolute validity continuing to run.

The affected source is restricted to unsealed `src/inet/linklayer/lowpan/` codecs, owner and NED configuration. Existing stateless calls retain defaults. Proposed direct verification: `LowpanStatefulContexts` unit and protocol cases, then existing `LowpanIphc*`, `LowpanNativeReassembly`, `LowpanNativeFragmentBoundaries` and the focused enabled/feature-off matrix. Packet ownership and first-fragment normalization retain the existing packet API; no sealed source is modified.

## P10 execution stages

A shared wire-value prerequisite, `icmpv6: fix: retain every neighbor option byte value`, gives `Ipv6NdOptionTypes` an explicit eight-bit underlying type through the supported MSG property. The unfixed enum's enumerators span only 1–8, so storing registration type 33 or unknown wire types invokes undefined C++ behavior. Preserve the enum-typed API and every wire value without inventing a sentinel option. Extend `Ipv6NdRegistrationWire.test` for raw option values, retain the ordinary `Ipv6NdUnsupportedRegistration` module and native `LowpanNeighborRegistration.test` consumer checks, and provide `nd-option-values.md` explaining the value contract and probe limits. This is a generic representation repair; it adds no registration policy or dependency on optional LoWPAN code.

The first prerequisite commit is `lowpan: add: owned expiring neighbor bindings`: only `LowpanNativeLinkDomain` storage/lookup operations, their independently useful ownership/expiry contract, a release fragment and `LowpanOwnedBindings.test` direct module checks. It does not change adaptation packet handling. `LowpanDynamicBindings.test` radio checks and explicit native-destination handling belong with the following server behavior/protocol fixture. This keeps the new storage mechanism independently reviewable before its production caller.

The local registration server precedes host discovery and the multihop registration exchange. Its behavior commit is `lowpan: add: native address registration server`, with `LowpanNeighborRegistration.test` and `neighbor-registration.md`. Default `nativeNdRole="static"` preserves the static profile; `"router"` enables this stage only on interfaces containing `LowpanNativeBoundary` and requires IPv6 forwarding. Native control messages always use computed wire checksums; the inherited checksum setting continues to govern ordinary interfaces. Compatibility interfaces retain their existing behavior. Later host and border-router role commits need separate production cases before P10 is complete.

ND bounds its module-wide table and owns one expiry timer. Keys are IPv6 interface ID and registered IPv6 address; values retain ARO owner EUI-64 separately from actual native address and deadline. Validate code, checksum, Hop Limit, a local permanent NS target, unicast non-unspecified source, one native SLLAO and one valid length/status ARO before mutation. Ignore reserved ARO bits on receive. This closed native profile requires SLLAO to match actual receive metadata. Same owner refreshes; another owner returns duplicate without changing the incumbent; a new entry at capacity returns cache-full. Zero lifetime and exact expiry remove only that registration. Errors go to the owner's EUI-derived link-local address; success goes to the registered source.

Dynamic domain bindings record owner and absolute expiry; static bindings remain intact. A conflicting static identity returns duplicate. Lookup rejects expired dynamic entries independently of event order. Translate IPv6 interface IDs to domain module IDs explicitly. ND owns each learned /128 route and removes only routes bearing its source/interface/address, scanning rather than retaining route pointers. Removal/replacement also purges the destination cache. A validated explicit native request permits unicast replies before a binding exists. Stop, crash and destruction cancel timers and remove owned bindings/routes while preserving unrelated state. The native protocol fixture omits static neighbors on learned links and observes NA radio transmission, later data resolution, refresh, duplicate/cache-full, zero lifetime, expiry and restart.

A separate `lowpan: add: native router advertisements` commit first supplies the independently usable RS responder, with `LowpanRouterDiscovery.test` and `router-discovery.md`. It honors the per-interface advertising flag, validates literal native RS input, schedules bounded owned unicast responses with the RFC 6775 randomized delay of up to two seconds, cancels pending responses on lifecycle cleanup, and observes real unicast RA fields, off-link prefixes, remaining advertised lifetimes calculated when emitting and preservation of existing bindings. The following host/discovery stage is `lowpan: add: native router discovery and registration refresh`, with a separate production fixture `LowpanHostRegistration.test` and `host-registration.md`. A host sends non-unspecified link-local RS with native SLLAO and bounded retransmissions. A router replies by unicast RA with SLLAO and off-link PIOs. Host RA processing records the router's native next hop, default route and lifetimes, ignores PIO L=1, configures EUI-derived addresses where allowed and starts unicast ARO registration for its addresses. Successful NA records the accepted lifetime and schedules refresh before expiry; retries are bounded, duplicate status stops using the address, and cache-full or unreachable routers trigger another discovery choice. Registration control must remain usable before data registration succeeds; ordinary data must not use a failed registration. Tests observe real RS/RA/NS/NA exchanges without static neighbor bindings, subsequent routed data, refresh, retry exhaustion and mixed ordinary interfaces.

Native SLAAC follows [RFC 4862 section 5.5.3](https://www.rfc-editor.org/rfc/rfc4862.html#section-5.5.3), including its repeated-PIO valid-lifetime update rule and independent preferred lifetime. Track auto-configured addresses separately from manual addresses. The selected host profile uses M=0 and 64-bit EUI-derived IIDs; DHCPv6 assignment is not inferred from receiving M=1. Host data from pending/failed registrations drops observably; generated ND control traffic remains usable for registration. Prefix advertisement converts positive absolute `AdvPrefix` deadlines to remaining seconds, negative values to relative lifetimes and zero to the infinite wire value.

Native hosts also answer valid unicast Neighbor Solicitations for their usable assigned addresses with solicited Neighbor Advertisements. An ordinary reachability probe need not contain an ARO or SLLAO; it must not enter the registration-request path or the ordinary Ethernet address decoder. The host fixture observes a real radio reply to a zero-option probe after registration and rejection of invalid or expired targets, preserving the reachability behavior required by [RFC 6775 section 5.5.3](https://www.rfc-editor.org/rfc/rfc6775.html#section-5.5.3).

The independently usable router responder precedes the host client in `lowpan: add: native neighbor solicitation responses`, with `LowpanNeighborRegistration.test` and `neighbor-registration.md`. The ND owner validates ordinary native NS messages separately from ARO requests and replies for valid assigned targets. Unicast replies may omit TLLAO with Override clear; multicast router solicitations require native TLLAO. A valid unspecified-source DAD probe receives an all-nodes advertisement with Solicited clear and native TLLAO. Router-role flags, computed checksums and explicit actual native reply destinations are observable in the reused registration fixture. The host client then calls the same responder without introducing another state owner.

Before the native host caller, a generic `ipv6: add: query interface address validity` prerequisite supplies read-only `Ipv6InterfaceData` deadline and explicit-time validity queries. Existing `hasAddress()` ignores validity and stays compatible. The focused `Ipv6AddressLifetimes.test` unit checks finite/infinite and missing addresses, the exact deadline and updated lifetimes without mutating address membership. This avoids inventing a permanent-only restriction for manually configured native addresses. `LowpanHostRegistration` is an ND-owned helper for bounded host policy/timers; the ND module retains simulation scheduling, gates, interface/route coordination and lifecycle ownership. No new generic module or callback interface is introduced merely to split the implementation file.

Multihop registration is a separate behavior commit, `lowpan: add: routed duplicate address registration`, with `LowpanMultihopRegistration.test` and `multihop-registration.md`. A 6LR holds a tentative entry while DAR/DAC travels to a configured 6LBR through IPv6 routing; tentative entries supply no data route. Match address and owner on confirmation, bound retries and follow the RFC 6775 timeout policy deliberately. A separate 6LBR DAD table rejects another owner without modifying the incumbent. DAR/DAC uses routed Hop Limit 64 and is exempt from the single-hop 255 receive rule. The fixture needs an actual multihop path through an ordinary-interface transit router, simultaneous registrations, duplicate and timeout outcomes, de-registration, exact expiry and restart cleanup.

Its independently usable authority precedes the relay in `lowpan: add: routed registration authority`, with `LowpanRegistrationAuthority.test` and `registration-authority.md`. The 6LBR role accepts DAR over ordinary routed interfaces, owns a bounded address/owner/lifetime table and emits real routed DAC without creating native neighbor bindings. The fixture sends literal DAR through an Ethernet transit router and checks compatible Code handling, owner refresh/conflict, capacity, matching removal, exact expiry and lifecycle cleanup. These observations establish the authority independently of the later 6LR pending-state caller. The relay uses an explicitly configured valid assigned non-link-local DAR source; DAC uses the request's currently valid local non-link-local destination as its source, preserving authority matching without duplicating route selection.

Before the authority, `lowpan: fix: reject malformed neighbor discovery before dispatch` guards the optional IPv6 receive path, with `LowpanNdWireValidation.test` and `nd-wire-validation.md`. Generic IPv6 peeks ICMPv6 with strict chunk flags before ND policy can reject an incorrect or incomplete message. The existing `LowpanIpv6` override safely recognizes ND types 133–137 and DAR/DAC types 157–158 and consumes malformed wire input before that strict peek, without changing generic or sealed packet code. Static-role protocol coverage proves malformed registration Code/length drops, zero-length NS options, truncated RA options, safe unsupported valid DAR handling and preservation of ordinary ND. The authority then uses this validated receive path rather than owning the parser repair.

The selected multihop profile has one configured DAD authority per 6LR and allows an ordinary-interface-only 6LBR. Enabling this profile checks every requested address, including EUI-derived addresses for which RFC 6775 permits omitting this check. Initial registration waits for confirmation; an existing valid registration remains usable during same-owner asynchronous refresh. Same-owner repeated requests coalesce without resetting the bounded DAR attempt count; another owner cannot replace a pending request. Pending state expires after 20 seconds, DAR retries use the one-second retransmission interval and three-attempt bound, and exhaustion follows the RFC 6775 section 8.2.6 recommendation to answer success. Tests distinguish this fallback from confirmed uniqueness. Zero-lifetime requests propagate removal to the authority. A configured authority and the response address/owner must match before a DAC changes state. The 6LBR table never installs a native neighbor binding.

DAR receive validation resolves the conflicting RFC 6775 sections 4.4 and 8.2.1 in favor of section 4.4's Code-ignore rule and RFC 8505 section 6.4's explicit legacy interoperability flow. Legacy transmission uses Code zero and an eight-byte owner; legacy reception accepts the compatible eight-byte extended form and ignores its transaction field. This choice does not claim conformance to section 8.2.1's contradictory literal Code-zero condition. P11 interprets the Code suffix and variable owner lengths explicitly; unknown extended suffixes are unsupported rather than assigned a guessed length.

The following behavior commit, `lowpan: add: authoritative context advertisement distribution`, has `LowpanContextAdvertisements.test` and `context-advertisements.md`. RA distribution associates each complete 6CO/PIO set with its ABRO, decrements PIO/context remaining lifetimes, rejects older versions and removes the associated information on ABRO expiry. Different authorities have separate version spaces and separate outgoing advertisements. Context compression eligibility expires before the receive-only grace period; exact deadlines must hold independently of timer event order. Explicit zero-lifetime 6CO removes immediately, whereas ABRO zero means its default lifetime. The fixture covers native multihop propagation, context replacement/retirement/deletion and restart cleanup. Full P10 remains open until registration, discovery, multihop DAD and authoritative context distribution pass.

## P11 transaction-order policy

Keep the RFC 8505 section 5.2.1 comparator separate from the registration owner's selection policy. Apply the written absolute-difference window literally: `(240,5)` prefers 240, `(250,5)` prefers 5, `(250,240)` prefers 250, while `(127,0)`, `(0,127)` and `(10,27)` are incomparable. Increment still wraps circular 127 to zero. The referenced RFC 6550 section 7.2 repeats this gate; it supplies no special wrap exception. Do not substitute modular distance or use packet arrival time as evidence of source-generation order without declaring a different interpretation.

The selected conservative reconciliation retains a live incumbent when increment recency cannot be established, without refreshing its expiry solely from an incomparable request. It does not relabel `INCOMPARABLE` as `OLDER`. Once that state expires, a fresh request can establish state without the former comparison. This can interrupt renewal continuity at 127-to-zero wrap; tests must report that behavior rather than claiming seamless wrap. The client retry/discovery path remains bounded and can register after expiry. Preserve comparator outcome and policy disposition separately in diagnostics and tests, including equal TIDs, stale de-registration, wrap, delayed reverse-wrap values and incomparable requests before/after expiry. Use actual wire fields and owner state, with no simulator-only source-generation oracle.

## Advanced forwarding contracts

P12 parses and forwards outer Mesh/BC0 before inner dispatch processing or reassembly. Mesh addresses remain originator/final identities while immediate MAC addresses change at every hop. Final reassembly and IPHC derivation use the mesh identities. Mesh hop count decrements before forwarding and cannot wrap from zero. BC0 sequence allocation, duplicate-cache capacity and expiry are explicit model policies; RFC 4944 does not specify the flooding algorithm. The native MAC continues to use its supported extended unicast and short broadcast profile. Wire helpers cover both short and extended Mesh address fields. A three-node fixture must observe early forwarding, unchanged IPv6 Hop Limit, original/final identity preservation, broadcast duplicate suppression and hop exhaustion.

P13 keeps dispatch-page state local to each packet. Paging is recognized on every page; unsupported-page payload is never interpreted as page zero. IPHC has the same meaning on pages zero and one. Mesh and RFC 4944 fragmentation precede the first page-one switch. ESC is `0x40` followed by an EET octet; there is no generic extension-length byte. Unknown EET processing drops at an endpoint, while an outer mesh transit path can preserve opaque bytes without interpreting them. Independent packet tests must prove page reset and a transit/endpoint distinction using the same unknown EET bytes.

P14 requires an explicit native transmission-completion contract before forwarding depends on first-fragment success; the present MAC destroys completed frames without notifying adaptation. This is a prerequisite mechanism with direct completion/failure tests, not a simulation signal used to drive protocol state. The forwarding owner must resolve the actual IPv6 route and native next hop on FRAG1, decrement the IPv6 Hop Limit, allocate an outgoing tag and install a bounded VRB atomically. A failed first transmission releases that state before later fragments can proceed. Missing-VRB nonfirst fragments drop. The owner can retain outgoing tail bytes when a different header-compression result reduces first-frame space, and must pace subsequent frames. Callbacks, timers and unsent fragments need lifecycle cleanup. The production fixture must prove that a relay transmits before complete datagram reception and that failed first-hop delivery, tag collisions, route changes, capacity and expiry cannot leave usable stale VRBs.

P15 uses its own six-byte RFRAG/RFRAG-ACK representation, eight-bit tag allocation and compressed-byte coordinates. Fragment sequence identifies a bitmap bit, not a byte offset. Sequence zero's offset field contains the total compressed datagram size; this follows RFC 8931 section 5.1 despite the inconsistent introductory sentence in section 4.4. Source fragmentation leaves first-frame slack for the possible eight-byte IID expansion; relays adjust total size and later offsets by their compression delta without refragmenting. Reverse ACK mappings include interface/native identity/tag. Unknown forward state returns NULL ACK; unknown reverse state drops silently. Source retry windows, bounded RTO/backoff, oldest-missing-first recovery after the initial send, ECN echo and short completed-datagram retention are owned state. FULL means `0xffffffff`, including unused bitmap bits; NULL aborts. Receive completion requires byte coverage and delivery exactly once. Preserve the first-fragment reconstructed address snapshot through context expiry, without changing compressed coverage coordinates. Loss-injection fixtures must disable or exhaust local MAC retry for the selected lost frame so an observed retransmission establishes end-to-end recovery rather than only MAC recovery.

## Progress

P10/P11 use RFC 6775 and RFC 8505 individual unicast-address registration, including the RFC 8505 base-peer compatibility flow. Later updates are explicitly outside this package: RFC 8928 cryptographic AP-ND, RFC 8929 backbone federation, RFC 9010 RPL signaling, RFC 9685 multicast/anycast subscriptions and RFC 9926 prefix registration. ROVR comparison is an ownership identifier match, not cryptographic proof. The generic ICMPv6 wire prerequisite precedes native registration policy; it preserves variable-length options and decodes DAR/DAC subclasses without a dependency on the optional LoWPAN feature.

P10/P11 first add the separately reviewable generic ICMPv6 wire prerequisite: `Ipv6DuplicateAddressHeader` supports DAR/DAC and extended 8/16/24/32-byte ROVRs through the ordinary ICMPv6 serializer and `Ipv6NdMessage` dispatch. Raw ND options, including variable-sized link-layer addresses, retain their bytes without optional LoWPAN dependencies; existing eight-byte Ethernet options remain typed. Proposed direct coverage is `tests/unit/Ipv6NdRegistrationWire.test`, selected by `opp_run_unit_tests --load . -p inet -m debug --no-build -f 'Ipv6NdRegistrationWire\.test$'` after a fresh debug build. Ordinary ND safely drops unsupported registration messages and address representations; `Ipv6NdUnsupportedRegistration.test` checks the ordinary IPv6-to-ND receive path. This prerequisite does not claim registration policy or live native ND integration.

P9 is split into a wire-representation/nested-IID preparation commit with `LowpanExtensionNhcWire` unit vectors, a chain-codec commit with independent chain vectors, and production integration with `LowpanExtensionNhc.test` and its reviewer document. Preparation does not claim live extension compression before the production caller is connected.

P9 runtime regression exposed a shared IPv6 prerequisite: local delivery stored a decoded Fragment header's raw pointer after its scan-local owning chunk was destroyed. Preserve a shared chunk reference through reassembly in a separate `ipv6: fix:` commit, verified by literal serialized fragments and the affected route-over/source-fragmentation cases, before enabling NHC reconstruction.
